# 아키텍처 명세서

## 1. 개요
- 현재 Streamlit 기반 단일 페이지 앱 구조를 유지하면서, 서비스/유틸 레이어를 명확히 분리합니다.
- 세션 관리와 컨트롤러(`MainController`)는 기존대로 사용하되, UI 컴포넌트는 가벼운 뷰 역할만 담당하도록 합니다.

## 2. 주요 컴포넌트
- **UI 레이어**: `app.py`, `ui/components/`, `ui/controllers/`
  - 템플릿 렌더링, 사용자 입력 수집, 상태 표시.
- **서비스 레이어**: `ui/services/`
  - 이미지 처리, 응답 포맷팅, 채팅 내보내기 등 비즈니스 로직.
- **도메인 로직 레이어**: `src/rag/`, `src/processing/`
  - RAG 체인 제어, 전처리 모델 선택과 실행.
- **유틸리티 레이어**: `src/utils/`
  - 공통 로깅, 퍼포먼스 측정, 텍스트 후처리.

## 3. 변경 사항 요약
1. `AppService`를 책임 단위로 나누고, 이미지 분석 관련 헬퍼는 `src/utils/image_tools.py`(신규)로 이동 예정.
2. 채팅 컴포넌트는 `AppService`의 결과만 받아 표시하도록 수정.
3. 전처리 모델이 공통으로 호출할 추출 헬퍼를 `src/processing/document_pipeline.py`(신규)로 생성.
4. `RAGChain`에서 모델 토큰 정보는 `LLMManager`의 헬퍼 함수만 호출하도록 단순화.

## 4. 데이터 흐름
1. 사용자가 질문 입력 → `chat_interface`가 컨트롤러를 거쳐 `RAGChain`을 호출.
2. `RAGChain`은 문서 검색/전처리 후 응답을 반환.
3. 이미지 정보는 응답 메타데이터와 문서 메타데이터에서 추출 → `AppService`의 이미지 헬퍼가 경로를 정리.
4. UI는 정제된 텍스트와 이미지 경로만 받아 화면에 표시.

## 5. 비동기 및 스트리밍 처리
- 스트리밍 응답 핸들러를 `ui/services/streaming_service.py`로 분리해, UI는 상태 업데이트만 수행합니다.
- 용어(설명: 전문 분야에서 쓰이는 어려운 단어) 예시 → `스트리밍`: 데이터를 조금씩 끊어서 전송하고 즉시 화면에 보여주는 방식.

## 6. 확장 고려 사항
- 이후 새로운 이미지 공급자나 전처리 모델이 추가되더라도, 공통 헬퍼에만 확장 코드를 추가하면 됩니다.
- UI와 비즈니스 로직을 분리했기 때문에 테스트 코드 작성이 쉬워집니다.
